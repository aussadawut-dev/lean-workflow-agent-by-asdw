## Findings and proposed design

Existing baseline: TCK024 and .lean/CHANGELOG.md document 5.7.0's optional Stop gate tier, session contracts, tracker threshold, hook read-only fast path and receipt history. These are not new feature proposals. Local config currently sets tracker/direct only; PROJECT.md has a full gate but no Stop tier.

Repository evidence:
- .lean/lean/activity.py: record/load/phase_durations/summary provide local activity and aggregate durations; phase grouping is by task label, and task filtering retains non-phase events. This is insufficient for trustworthy per-task attribution across sessions. No historical baseline was available from this checkout's `lean log --summary` beyond the current research phase.
- .lean/lean/testsel.py: run_files already parallelizes test files and prints per-file timing, but persists aggregate timing. gate.py executes checks sequentially, prints per-check timing and supports opt-in whole-tree reuse. Further parallelism is not automatically a win.
- .lean/lean/evidence.py: state fingerprints HEAD, controls, index and Git-visible content including submodules. Smaller cache keys require explicit dependency coverage; ignored/environment inputs must not be silently treated as covered.
- .lean/lean/records.py: context_command already summarizes work for resume. Extend this instead of creating a second memory store.

Options, ordered by recommended investigation priority:

1. Measurement first: extend activity events with stable task/session/run/check identifiers, individual check/test duration, reuse reason and retry classification. Summarize elapsed time, check time, rework and missing observations separately. Provider-reported token counts are optional with provenance; unavailable usage stays unknown, never zero. Acceptance: interleaved-session fixtures attribute events correctly; no double counting nested test/gate duration; raw events reconcile with summaries. Cost: event schema/retention work. Start with local JSONL and the standard library.
2. Explain the existing plan: a proposed read-only `lean plan --explain` (name tentative) derives affected tests, review floor, gate tier and reuse eligibility from existing selectors and evidence checks. Acceptance: fixtures agree with actual selection; unknown dependency coverage falls back to existing conservative behavior; no writes, validation pass or scope authorization from the preview. Cost: keeping preview and execution on one shared implementation. This improves predictability and avoids discovering prerequisites after an expensive run.
3. Compact resume context: extend `lean mode context` with source paths/state, accepted decisions, unresolved acceptance and next action; allow a bounded output budget while retaining critical obligations. Acceptance: stale state is identified, source references resolve, and scenario tests retain all acceptance blockers. Cost: freshness and truncation semantics. Do not duplicate authoritative rules or invent a second knowledge database.
4. Per-check evidence reuse: only after measurement shows reruns dominate. Explicitly declare each check's inputs, command/config and runtime dependencies; invalidate on relevant changes and disable reuse for undeclared external inputs. Preserve final gate and review requirements. Acceptance: mutation matrix for source/test/config/runtime/submodule inputs never reuses invalid evidence; equal validated inputs can reuse eligible checks. Highest risk and maintenance cost because it touches gate trust. Separate HIGH-risk design/review required before implementation.

No-change/configuration-only alternative: evaluate existing Stop tier/session contract/tracker threshold on a representative consumer project before adding features. These options change workflow policy and remain unmodified here. They may provide the cheapest improvement, but benefits are unmeasured and settings must match project risk.

Recommended experiment: collect a paired baseline/candidate sample of docs-only, narrow bugfix, cross-file feature, HIGH-risk control edit and resume-after-interruption work. Compare median/tail latency, tool calls, observed tokens, repeat checks and rework with identical acceptance and review floors. Exclude or separately report user idle time and missing usage. Start with a small pilot; expand before making tail-latency claims. Choose numerical improvement targets after baseline collection; reject regressions in acceptance or evidence validity. Do not count this research session's overhead as representative coding performance.

Suggested first implementation scope, if selected later: measurement plus one summary view, then explain-plan. Keep model auto-routing, mandatory multi-agent execution, remote dashboards and per-check caching out of the first increment. They add complexity without current bottleneck evidence.
