# TCK016 — Bounded requirement intake and batch closure

Status: DONE
Owner: Codex / current session

## Goal

Give tracker/direct a small, optional durable requirement intake and shipping-batch boundary. Preserve whole-checkout evidence semantics and existing installations.

## Acceptance criteria

- [x] AC-01: Every intake entry has an ID, classification, task and observable acceptance; active/queued/superseded/cancelled entries remain traceable. Invalid dependencies, cycles, missing traceability and duplicate primary ownership are refused deterministically.
- [x] AC-02: New features queue by default. One active batch per Controller; explicit interruption requires a checkpoint. Workers remain subtasks. Selection follows explicit user priority, blockers, dependencies, finish current, then next feature; no invented numerical ranking.
- [x] AC-03: Freeze records the batch requirements and contract before review. New intake stays queued; changing frozen scope requires explicit reopening with a reason and reports evidence invalidation. Findings may be fixed within frozen scope; existing receipts detect content drift.
- [x] AC-04: Readiness reports implementation, review and gate independently; deferred/NOT_RUN is not an implementation failure or PASS. Existing review and gate still cover the whole shipping checkout, not isolated tasks.
- [x] AC-05: Meaningful fail-before/pass-after regressions, affected tests, deterministic validation, independent HIGH review and shared gate pass on final shipping state.

## Tasks

- [x] TASK-01: Add opt-in intake/batch CLI and invariants, available without full-mode leases.
- [x] TASK-02: Add regression coverage and update workflow procedure/docs with bounded sequencing and follow-ups.
- [x] TASK-03: Validate, independent review, gate and map acceptance to evidence.
