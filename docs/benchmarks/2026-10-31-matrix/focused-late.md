## Late evidence, single-pass source investigation

Keep every applicable safety, quality, dependency and workflow requirement. The parent owns shipping validation and the full gate; this child only returns the authorized source analysis. Do not mark whole-project DONE or claim unrun tests.

Order context by when it is needed. Large source reads should happen after startup bookkeeping so their tokens are not retransmitted for preliminary mode/phase operations. Use this sequence:

1. Read only the mandatory `AGENTS.md .lean/README.md .lean/PROJECT.md` together first. Do not dump a whole source packet at startup. The question already supplies starting paths.
2. Declare the exact question contract once with the release's standalone contract command, without chaining it.
3. In one following tool/shell batch, run `python3 .lean/bin/lean mode show` and `python3 .lean/bin/lean progress set scope --task 'Source investigation'` and read the known starting implementation/test paths. Locate any unknown names with a narrow search in that same batch. Valid phases are `contract scope implement test validate review gate done`; no inspect/investigate phase exists. The question is accepted scope for this analysis-only child. Product implementation, application-test and full-gate phases are not authorized here.
4. Follow material imports, callers, schemas and tests in batches of complete relevant functions/test cases. Read complete small modules; use symbol-bound excerpts for large registrars, schema files or suites. Keep path:line references. If output is truncated or a boundary is incomplete, expand it before claiming what it does. Avoid broad full-file dumps just to find a few registrations or test assertions. An optional `source-context.md` exists, but retrieve only a missing relevant section rather than injecting the entire packet.
5. Once all requested questions have decisive source/test evidence and honest limitations, combine any last missing evidence reads with `python3 .lean/bin/lean progress set review --task 'Check source evidence and limitations'`, check the conclusions against what is already held, and answer. Do not re-fetch unchanged source, re-state the plan, or add a separate tool call solely to repeat a mode/progress operation.

Load a routed policy body when there is a real unresolved rule or procedure. The applicable phase vocabulary and source-only completion boundary are explicit above; do not load WORKFLOW/CONTEXT merely to repeat instructions already available.

Bound claims to the actual question. For an API contract, caller-ID selection plus strict schema/HTTP tests can answer the contract while explicitly relying on shared middleware; do not turn it into a new exhaustive audit of shared auth/entitlements. For tenant, network or concurrency questions, inspect the material boundaries and interleavings. Separate what source demonstrates from what remains unverified; never infer safety from a mock, a name or an omitted excerpt. Stop adding adjacent feature investigations once the requested claims and limitations are supported. This sequence is not a hard call cap: missing material correctness or security evidence requires expansion.
