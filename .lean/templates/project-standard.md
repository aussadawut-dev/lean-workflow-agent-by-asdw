# Project standard record

Adapt this format inside existing project documentation. Copy only when a project record is authorized; this template grants no approval. Select relevant areas rather than creating a complete category tree. Keep stable IDs when wording changes and record material revisions.

- ID and title: project-chosen stable identifier.
- Version / updated date: revision of this rule.
- Status: proposed | accepted | deprecated.
- Strength: mandatory | recommended (advisory; nonconformance does not block work).
- Applies to: behaviors, components and conditions covered; exclusions.
- Rule: observable requirement.
- Rationale: problem addressed and relevant trade-offs, including the current approach.
- Evidence: repository paths, accepted scope/decision references, researched source links and versions/dates; uncertainties.
- Verification: applicable source, test, runtime or manual checks and required evidence.
- Acceptance: approval reference and decision date; leave unapproved rules proposed.
- Exceptions: scope, reason, approval reference, limits and review condition if relevant.
- Supersedes / replacement: related IDs and explicit migration scope, if any.

Research recommendations alone do not establish a mandatory project standard. Preserve the decisions applicable to historical work; adoption does not silently authorize migration.
