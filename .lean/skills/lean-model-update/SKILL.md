# Lean Model Update

Input: `$ARGUMENTS`, or the current task when substitution is unavailable (default: every configured provider). Resolve procedure intensity under `.lean/policy/SKILL-EFFORT.md`; keep model reasoning effort separate. Read `.lean/policy/MODELS.md` first. This skill changes only the project's `.lean/models.json`, never session, global or provider settings.

1. **Research** (`/lean-research`). List what each provider offers now: `lean models check --live`, the Codex model cache, `agy models`, and the runtime's model list for Claude (its CLI lists none). Add official release notes for anything new. Report new, retired and untested models and efforts with dates and sources; mark unverified claims.
2. **Eval plan** (`/lean-scope`). Draft `{"candidates": [{"provider", "model", "effort"}], "tasks": [sizes]}` with the user: which models and efforts, which sizes of the task bank (`lean models bank` lists and checks it), and a hard token cap. Estimate the cost from earlier results (`docs/benchmarks/*-models*/`). Wait for the user's approval of the plan and the cap; never pick a cap yourself. Leave out Codex `ultra` (automatic delegation) unless the user asks for it.
3. **Permissions.** Headless CLIs cannot ask for permission. `lean models eval` runs Claude and Codex with the `models.json` arguments plus eval-only flags (Claude may run `python3 -m unittest`); nothing is written to any settings. agy denies every command and file write unless the user has allow rules: give the user the exact command to add `command(python3)`, `command(git)`, read-only commands and `write_file(<run folder>)` under `permissions.allow` in `~/.gemini/antigravity-cli/settings.json` (the eval prints the run folder; it is outside the repository), and to restore the file afterwards. Never edit those settings yourself and never add a flag that skips permissions; without the rules, leave agy out and say so. A denied tool is reported as a note; only the score decides.
4. **Eval.** `python3 .lean/bin/lean models eval --plan <plan> --budget <cap> [--estimate <tokens>]` (results in `docs/benchmarks/<date>-model-eval` unless `--out` says otherwise). It removes metered API keys, runs each candidate on each task in a throwaway copy outside the repository, scores hidden tests and writes `results.jsonl`, `summary.md`, `proposal.json` (with its sha256) and raw `logs/`. Each run reserves the larger of the largest token count seen and `--estimate` (default 250000), starts only while spent plus reservations fit the cap, and otherwise waits for running ones to finish; it is skipped only when nothing is in flight and it still does not fit. The cap can be exceeded only by a run that uses more than its reservation; say so when reporting. Set `--estimate` from earlier results for the largest size in the plan. A rerun with the same `--out` resumes. Report the cap, what ran and what was skipped; never raise the cap without the user.
5. **Review** (`/lean-review`, HIGH depth, independent reviewer). Give the reviewer the plan, `summary.md`, `results.jsonl`, `proposal.json`, `logs/` and `solutions/`, not your reasoning. It checks that each proposed size is the fastest full-score candidate, that skipped or denied runs and estimated tokens are disclosed, and whether one task per size supports the change; a size with no full-score candidate keeps its current mapping. The hidden tests run in the candidate's own Python process, so a solution could fake a pass by patching `unittest`: the reviewer reads the solution (in `solutions/`) of every run the proposal uses.
6. **Proposal.** Show the user the per-size diff against the current `models.json` (old → new per provider), the evidence behind each change and the limits (one run per setting, one task per size). Apply only after the user approves that exact proposal: `python3 .lean/bin/lean models apply --proposal <out>/proposal.json --sha256 <digest>`, then `lean models check --live`. A changed proposal needs a new approval.
7. Record the plan, cap, results, review and the user's decision in the owning tracker (tracker/full mode) and keep the results folder in the repository. Changes to `models.json` follow the normal contract, tests, gate and review. No commit, push or release without the user.
